# Click Indicators — compatibility with other Geode mods

**Mod:** `jackz.click-indicators` v1.0.3 · Geode 5.7.1 · GD 2.2081 (Windows only)
**Document date:** 2026-08-01
**Status of everything below: PREDICTED, NOT OBSERVED.**

## What this document is

Click Indicators reads macro files and draws an on-screen cue for the frame to click. To do that it hooks 13 functions, writes seven pieces of state that Geometry Dash and other mods also own, and assumes the game steps physics at exactly 240 Hz. This document is the full list of places where those choices can collide with another mod, written from a line-by-line read of our own source plus the source (or, where source was unavailable, the shipped binary) of the mods most likely to be installed alongside us.

Three things about it should be stated up front, because they determine how much weight it deserves:

1. **Nothing here has been tested in game.** Every entry is a prediction derived from reading code. No interaction in the per-mod matrix has been reproduced, confirmed, or refuted by running Geometry Dash. Section 5 exists to change that: each row has a literal procedure with a pass and a fail condition, and every row's status stays `untested` until someone has run it and written down which one happened.
2. **Some of the worst findings are about our own code, not about anyone else's.** Section 3 comes before the per-mod matrix deliberately. The hardcoded 240 Hz physics rate and the unprioritised `GJBaseGameLayer::handleButton` hook are ours, they are wrong on their own terms, and they are the root cause of a large fraction of the per-mod rows. Several rows disappear entirely once those are fixed.
3. **Where a claim could not be sourced, it says so.** Confidence is marked `high` / `medium` / `low` / `unknown` per row. `unknown` means the source was not obtainable (Eclipse Menu's repository returns 404; Mega Hack is closed source; the GD-2.2081 xdBot build is an off-index binary fork) and the row rests on binary string extraction or on an older community fork, not on the shipped implementation. "Both hook the same function" is never on its own listed as an interaction — every row states the ordering, the shared state, or the violated assumption, and what the user sees.

Two conventions used throughout:

- **Hook ordering.** TulipHook sorts the detour chain ascending by priority (`Handler::reorderFunctions`, `std::sort` on priority only). Lower number = earlier in the chain = **outermost**. Geode's own aliases confirm the consequence: `VeryLatePost == VeryEarly`, `VeryEarlyPost == VeryLate`. So for a hook whose body is `Original(); <work>`, a *lower* number makes the work run *later*. The sort is **not** stable and is re-run whenever any hook is added or its metadata changes, so two mods that both sit at `Priority::Normal` have an order that is unspecified, can differ between machines, and can change during a session.
- **Severity vocabulary.** `wrong-results-silently` (the mod reports a number that is wrong, with no error) · `breaks-clickindicators` (our feature stops working or turns itself off) · `breaks-other-mod` (we damage something the other mod owns) · `cosmetic` · `none` (checked and clear — listed so the check is visible).

## 2. Known risks in our own code

Most serious first. These are defects and fragilities in Click Indicators, independent of any particular other mod. Line numbers are `src/main.cpp` unless noted.

### 2.1 The 240 Hz physics rate is a compile-time constant with no runtime detection — `high` confidence

```
188:  static constexpr double kPhysFps = 240.0;
194:  static constexpr double kPressLag = 1.0 / kPhysFps;
585:  static constexpr double REC_FPS  = 240.0;    // written into saved macro headers
790:  const double dt = 1.0 / 240.0;               // xtSimulate integrator step
4104: double dFrames = (pressT - a.sweet) * kPhysFps;   // the number the player is shown
```

240 Hz is correct for vanilla GD 2.2, and correct under a *speedhack*: the step quantum is `max(timeWarp, 1)/240`, so for `timeWarp >= 1` the factors cancel. It is wrong the moment anything changes the number of physics steps per frame, and wrong in four independent ways:

- **4104 is the headline claim.** `(pressT - a.sweet)` is a level-time error and stays correct at any rate; only the *unit* is hardcoded. At 480 TPS a genuine 2-step miss prints "1 frame" and passes the `close` test (`fi >= -1 && fi <= 1`, 4107). At 960 TPS a 4-step miss prints "1 frame". Below 240 the error inflates instead and "frame perfect" becomes unreachable. Accuracy %, streak, and the tracer colour all inherit the scaling.
- **194 is a bias, not just a scale.** `kPressLag` is meant to be exactly one physics step (the comment at 189-194 records why: `handleButton` is reached before `m_levelTime` is advanced for that step, established empirically by bot-replaying a macro and seeing a uniform −1 frame). At rate T the residual is `1/240 − 1/T`: +2.08 ms at 480, +3.13 ms at 960, −4.17 ms at 120. Always the same sign for a given rate, so every press reads systematically late or early. If the step length varies frame to frame (it does under carriers that compute it from the real frame delta) the residual becomes per-press jitter.
- **585/636 puts the false rate in a shared file.** `recSave` writes `fps: 240` into the header regardless of the rate the run was played at, and those files are saved into the level cache folder and are shareable. A macro recorded off-rate carries an invisible timebase error into every future grading of it, on other people's installs. This is the most damaging case because the bad data outlives the session.
- **790** exists specifically to model a rate artefact — the engine can only change speed on a step boundary, so the player spends up to one step at the wrong speed at each speed portal, and `xtSimulate` integrates that residual deliberately. At 480 TPS the true residual is half as large, so the simulation over-corrects, accumulating across a level.

Two further facts make this worse than a single wrong constant:

- **Our one rate sensor cannot see it.** `g_cal.h` (3437-3447) is level-time advance over wall-clock advance. A tick-rate change does not alter seconds-per-second, so `h` stays ~1.0 and there is no signal anywhere in the mod that the frame unit is wrong. The rate handling we *do* have is genuinely rate-correct for speedhacks (clamped to `[0.05, 64]`, EMA'd, with the frame-jump detector made rate-relative rather than a fixed threshold) — it simply does not cover this case.
- **A slow Time Warp trigger reaches this with no other mod installed.** Deriving from the published reimplementation of RobTop's step formula, for `m_timeWarp < 1` the modified-delta quantisation and the step count do **not** cancel and the step becomes `m_timeWarp/240` level-seconds. So inside a 0.5× Time Warp section a 2-step miss prints as 1. `medium` confidence — derived from a third-party reimplementation, not from the game binary, and it needs the in-game check in 5.3 before being asserted anywhere public.

The persisted state makes it outlive the cause. `cal-L` is saved globally, not per level and not per rate (267, 279, `calibSave` every 10 samples at 4174), and the observed x→t map is saved per level as `xt-<levelID>` (89, 117) with no rate tag and appended to during any run whose clock we trust (3520). One session at a non-standard rate can therefore mistime the guide on every other level, and on that level, permanently — after the cause has been uninstalled.

### 2.2 `GJBaseGameLayer::handleButton` has no hook priority — `high` confidence on mechanism

`ClickGuideInput` (4016) has no `onModify`, so the hook sits at `Priority::Normal` by default rather than by intent, even though the body deliberately calls the original first (4018) and then only observes. Three separate consequences:

- **Too outermost:** if a mod inside us swallows the input without calling down (input blockers, "don't click while X" gates, replay-with-ignore-inputs modes), our post-original code still runs, so we timestamp, **record**, and **grade** a press the engine never acted on. The trainer says you clicked, the icon did not jump, and a saved macro contains presses the level never received.
- **Too innermost:** if a mod above us swallows the input, we never see real presses. `g_dropStreak` climbs and the tripwire at 4050 fires "Start pos: guide is out of sync here - turned off", disabling the guide on a level where nothing is wrong. `g_btnDown` (4026) can also latch stuck-down, so the hold indicator is wrong.
- **Injected input is not addressable by priority at all.** A mod that *calls* `handleButton` to drive the player enters the chain from the top. There is no guard anywhere in the hook for "was this input synthetic" — the only filters are `g_recOn`, `button != 1`, `isGameplayActive()` and our own settings. Bot inputs are graded as the player's, fed into the start-offset anchor, fed into persisted calibration, and written into recordings.

Because the tie is resolved by a non-stable `std::sort` that is re-run on every hook add, which of the first two a given user gets is not controlled by anything either mod declares, and can differ between two launches. This is also internally inconsistent: we already made the innermost choice for `levelComplete` and `destroyPlayer`, and did not make it here.

Two smaller defects live in the same hook. `g_btnDown` is written at 4026 from **any** `GJBaseGameLayer`, including `LevelEditorLayer` — the record and grade blocks are correctly guarded by `PlayLayer::get()`, but that line is not, so editor playtest input leaves a stale hold state that can be wrong on the first frames of the next attempt (cleared in `resetLevel`, so the window is small; severity `cosmetic`). And the anchor push at 4068-4069 sits **above** the one-sample-per-action guard at 4096, so any mod that re-issues `handleButton` (dual-mode input mirroring, for instance) consumes two of the nine anchor slots per press.

### 2.3 `GameLevelManager::m_levelManagerDelegate` is assigned and nulled, never restored — `high` confidence, breaks GD itself

```
1340: glm->m_levelManagerDelegate = this;
1341: glm->getOnlineLevels(GJSearchObject::create(...));
1383/1647: if (glm && glm->m_levelManagerDelegate == this) glm->m_levelManagerDelegate = nullptr;
```

That is a single global slot. Concretely: the player is on a level list with an in-flight `getOnlineLevels` and owns the delegate; they open our macro popup and hit Search; we overwrite the slot; GD delivers the search completion to *our* `loadLevelsFinished`; the popup closes and sets the slot to `nullptr` rather than back to the previous owner; the original layer never receives its callback and sits on a loading circle. Any later GD search also has no delegate until something else sets one. Correct handling is save-and-restore of the previous delegate plus ignoring callbacks that are not ours. This is the one finding in this document that is not about another mod at all. `medium` confidence only on the exact visible symptom, since some layers re-set the delegate in `onEnter`.

### 2.4 The attempts / stat `"2"` rollback is a blind snapshot write-back — `high` confidence

```
3958: int attemptsBefore = m_level ? (int)m_level->m_attempts : 0;
3959: int statBefore     = gsm ? gsm->getStat("2") : 0;
3962: PlayLayer::resetLevel();
3970: m_level->m_attempts = attemptsBefore;
3971: gsm->setStat("2", statBefore);
```

Anything that legitimately changed either value between the snapshot and the write-back is destroyed — another mod's `resetLevel` hook that increments or corrects attempts, or anything the original did because another mod caused it. Stat `"2"` is a global counter (`high` confidence that it is global; `medium` that it specifically means total attempts), so a global is rewritten from a snapshot taken a few hundred instructions earlier.

**No priority fixes this.** Outermost makes us the last writer and therefore the one who clobbers; innermost makes us clobberable. The design is the problem. The order-independent form is a delta-undo: `if (after > attemptsBefore) m_level->m_attempts = after - 1;` — undo exactly the increment you caused and leave anything else alone. Same for the stat. We also read the stat through a hookable getter and write it back through a setter another mod may not hook, which promotes a display-only spoof into the real save file (`low` confidence that anything actually spoofs stat `"2"`, but the asymmetry is real).

Note separately that this rollback **cannot** reach a third-party tracker that keeps its own counter, and no amount of ordering changes that (see the BetterInfo rows in section 4). The cheapest fix for the whole class is to stop rolling the attempt counter back at all: percentage, completion and leaderboard are the cheat vectors and are gated separately, and our own comment at 3952 records the rollback as an annoyance rather than a requirement.

### 2.5 `PlayLayer::postUpdate` has no priority, and its body is not idempotent per rendered frame — `high` confidence

The body is `PlayLayer::postUpdate(dt); <every read and every draw>`, and every read is of live transform state: `m_objectLayer->convertToWorldSpace` (3603, 3750, 3761, 3788, 3807, 3845), `m_player1->getPositionX/Y`, `m_gameState.m_levelTime`. Two distinct problems:

- **Ordering.** Another mod that moves the camera or the object layer in *its* post-original `postUpdate`/`update` code and sits at a lower priority than us runs its move *after* we computed screen positions from the pre-move transform. Guide lines sit a constant few pixels off, or lag/jitter by one frame — for some users and not others, with no setting that changes it. Direction needed: `Priority::VeryEarly` (= `VeryLatePost`) so our drawing runs after every other mod's camera work. `medium` confidence that it is observable, since it depends on whether an installed mod actually does that.
- **Sub-stepping.** GD calls `postUpdate` from inside `GJBaseGameLayer::update`. Any mod that implements a tick-rate change by calling `update` in a loop runs our **entire** body once per physics sub-step instead of once per rendered frame: ~12 `getSettingValue` calls, a `CCDrawNode` clear and rebuild, and a `CCLabelBMFont::setString` with `fmt::format`. At 1000 TPS and 60 fps that is ~69× per drawn frame. It also poisons `g_cal.h`, because inside a catch-up loop `advance/dW` measures the catch-up ratio rather than game speed, and `dW` stays under our 0.1 s rejection guard, so the samples are accepted as legitimate. The fix is one guard: cache `CCDirector::getTotalFrames()` in `Fields` and return immediately after calling the original if it has not changed. That fixes every sub-stepping mod at once, not one of them.

### 2.6 `commitJumps` and `resetLevel` are unpinned while their two siblings are pinned — `high` confidence that the ordering is undetermined

Safe mode is implemented across four hooks. `levelComplete` and `destroyPlayer` are `VeryLate`; `commitJumps` and `resetLevel`, which implement the other half of the same feature, are not. `commitJumps` writes `m_uncommittedJumps = 0` **before** the original, so to be the last writer before the real function reads the field it needs the *highest* priority — `VeryLate`, matching its siblings. Unpinned, another mod's `commitJumps` hook sitting innermost can set the field back before the original reads it and safe mode leaks jumps; in the other direction a jump-counter feature reading that field in its own hook reads 0.

### 2.7 `PauseLayer::keyDown` at `VeryEarly` swallows 12 keys, and the stated reason for that priority is contradicted by our own comments — `high` confidence

```
4224: void keyDown(enumKeyCodes key, double timestamp) {
4225:     if (editorKey(this, key)) return;                    // no super call
4226:     if (freeCamPan(key)) { editorDraw(this); return; }   // no super call
4227:     PauseLayer::keyDown(key, timestamp);
```

Keys consumed: Z, C, X and Left/Right/Up/Down and A/D/W/S. At `VeryEarly` (−2000, outermost) this runs before every other mod's `keyDown` hook, so for those 12 keys those mods are not merely outranked — they are unreachable. Both gates limit the blast radius and should be stated in our favour: `freeCamPan` returns false unless the free-camera setting is on (default **off**), and `editorKey` additionally needs a captured frame and a loaded macro. But for users who turned free camera on, any pause-menu keybind another mod registered on those keys stops working with no indication that we are the cause. There is no priority that expresses "give me the key only if nobody else wanted it" — the outermost hook cannot know. The correct shapes are: call the original first and act only if the key was unhandled, or route through the keybinds API instead of a raw `keyDown` hook.

Compounding: `setKeyboardEnabled(true)` at 4238 widens dispatch for *everyone*. Any other mod's `PauseLayer::keyDown` hook that was previously never reached starts receiving keys, and their handlers were written assuming it never fires in the pause menu. We also never restore the previous keyboard-enabled state.

**And the justification is unresolved.** The comment at 4217-4220 says other mods hook `PauseLayer::keyDown` and were consuming the key ahead of us — which requires `keyDown` to be dispatched. The comment at 4234-4237 says `PauseLayer` never enables keyboard input so `keyDown` is never dispatched at all — which requires it *not* to be. One of these is a stale misdiagnosis, and it is the entire basis for the `VeryEarly` priority. `PauseLayer::keyDown` is a real function at 0x37ed10 so it is hookable either way; whether it is *dispatched* without `setKeyboardEnabled(true)` needs a live check (5.10). This is the priority a moderator is most likely to ask about, so the stated reason has to be the true one.

### 2.8 Zero cross-mod awareness, declarative or runtime — `high` confidence, verified by grep

`mod.json` has no `incompatibilities` and no `dependencies`. Geode 5.7.1 supports `incompatibilities` with per-entry id/version and a `breaking` flag, and emits "has unresolved incompatibilities" as a `LoadProblem` — so the loader-level mechanism for declaring the conflicts in this document exists and is unused. `src/` contains zero calls to `Loader::isModLoaded` or `getLoadedMod`, so at runtime we cannot tell the user that our measurements are not valid in their setup. When any row in section 4 fires, the user gets either silently wrong numbers or a bare "guide is out of sync here - turned off", with no attribution. That is the concrete shape of the maintainability concern: there is currently no channel through which the mod can say "the number I am showing you is not valid right now".

Also relevant and factual: `links` has `homepage` and `community` but no `repository` and no `issues`. For a submission whose stated blocker is long-term maintainability, a public issue tracker is the cheapest evidence available.

### 2.9 A macro arriving mid-attempt silently voids that attempt — `high` confidence

`downloadAndLoad`'s completion calls `loadActionsFromCacheFolder` + `markWebLoaded` whenever the level still matches, and that completion can land mid-run (the macro popup is reachable from the pause menu, and auto-fetch fires on level entry). `guideActive()` (2876) is just "`g_actions` non-empty && licensed && enabled", so it flips false→true the instant the download lands, and `attemptIsUnsafe()` (3925) then latches `safeTripped` on the next `levelComplete`/`destroyPlayer`/`commitJumps`. A run that was counting stops counting, mid-attempt, because a file finished downloading — and the only notification says "macro loaded" without mentioning safe mode. This is exactly the "my run didn't count and I don't know why" report.

Secondary: `loadActions` rebuilds `g_events` and resets `g_clickStats`, but `m_fields->nextTick` is a `PlayLayer` field and is **not** reset (only at 3429 on `jumped` and 3234 in `resetLevel`), so the audio cursor is left pointing at an index in a different array. Bounds-checked, so no OOB, but the outcome is a burst of cue sounds (capped at 8/frame) or silence for the rest of the attempt. Fix direction: defer the swap to the next `resetLevel`, or at minimum latch `guideActive()` per attempt the way `safeTripped` already does.

### 2.10 The rate estimator is reset every respawn and opens before it has converged — `high` confidence on the arithmetic

`g_cal.h` is reset to 1.0 in `resetLevel` (3991 area) and is an EMA with gain 0.1, so error decays as `0.9^n`: ~22 frames to get within 10%, ~44 to get within 1%. Its consumers open at `hFrames >= 15`, where `0.9^15 = 0.21` — still ~21% wrong. `lead = frozenL * h` is therefore mis-scaled for the first fraction of a second of **every** attempt whenever a speedhack is active, which on a practice level is constantly. `h` should persist across attempts within a session (it is a property of the user's speed setting, not of the attempt) and the readiness gate should be a convergence test rather than a frame count. The estimator should also reject samples that cannot be real-time: a genuine render frame advances at least two physics steps, single-stepping never does, and a catch-up loop produces a ratio no speedhack would.

### 2.11 The recorder's buffer selection and its save gate are both keyed on the wrong thing — `medium` confidence

- `recSave` (623) refuses to save when the **live** `g_startAlign != Exact`, but the buffer it would write is an older object. Any spawn whose declared `m_startSettings->m_startSpeed` disagrees with our portal walk by >1.0 u/s demotes `g_startAlign` to `Approx` globally for the rest of the attempt — common, because creators usually leave a StartPos's speed at default. So one start-pos switch can make a perfectly valid 0% recording unsaveable. The alignment needs to be a property of the buffer, maintained as frames are appended, not a global read at save time. The same latch also silently disables auto-calibration for the rest of the run (4130 area).
- `recBank`/`recBuffer` rank recordings by **absolute** last frame number (`recEndOf` returns `v.back().frame`, and frames are absolute level time × 240). A four-click fragment recorded from an 80% start pos therefore outranks a full 0% run, and the folder-picking heuristic then prefers the file with the greatest final release time, so that fragment permanently becomes the level's macro. Rank by coverage (last − first frame, or click count) and bank per spawn.

### 2.12 The persisted x→t map is written on a heuristic that a teleport can fool — `low` confidence on the trigger, `high` on the code

`bool realClock = !g_startKeyObj || (g_offsetLocked && g_offsetObserved);` (3519) decides that a run's clock is ground truth, and when true we append `(playerX, levelTime + offset)` pairs into `g_xt` and persist them under `xt-<levelID>`. There is no check that the position and time are actually compatible with a 0% run. Anything that moves the player without a `StartPosObject` — a checkpoint switcher, a restart-from-any-checkpoint tool, a jump-to-% tool, a noclip teleport, or a start-pos switcher that nulls the spawn while leaving `m_checkpointArray` populated — can make us write times that are low by a whole spawn time into a map that then persists across game restarts and survives uninstalling the other mod. The gate should be either agreement with `canonTimeAtX` within ~0.35 s, or an explicit per-attempt `startedAtZero` flag.

### 2.13 Screen projection discards rotation — `high` confidence on the code

```
3603: return overlay->convertToNodeSpace(m_objectLayer->convertToWorldSpace(ccp(worldX, py))).x;
```

We take only `.x` and then draw a screen-**vertical** segment. `convertToWorldSpace` walks the parent chain, so an inserted node or a scale is absorbed — including the mirror portal's negative `scaleX`, which is handled by ordering the two edges in screen space with `std::min`/`std::max` (3693-3694, with the regression it fixed written down above it). What is **not** absorbed is rotation: under a rotate-gameplay trigger or any mod that rotates the object layer, the set of screen points at a given world x is a rotated line, so every guide line, window bar and hold bar is drawn at the wrong place and angle. The timing path is rotation-aware (`canonTimeAtX` passes the StartPos's order/channel precisely because rotate-gameplay objects are gated on them); the gap is in the drawing path only.

*(Correction to an earlier internal note: there is no reference to `m_cameraFlip`, or to any mirror/flip field, anywhere in `src/` — verified by grep. The mirror handling is the screen-space min/max above. Any claim that we read `m_cameraFlip` is wrong.)*

### 2.15 Things in our own code that were checked and are correct

Stated because an honest audit has to include them and because several are load-bearing specifically for coexistence.

- **`m_isTestMode` uses the right direction and the narrowest window.** `VeryLate` = innermost, so the flag is true for the shortest possible time and is guaranteed true for the real function. Nested save/set/restore composes correctly with any other mod doing the same trick, in **either** order, so the conclusion does not depend on resolving priority direction.
- **The speedhack rate estimator is genuinely rate-correct** rather than assuming 1×: wall clock from `steady_clock`, ratio clamped to `[0.05, 64]`, EMA'd, and level-relative quantities divided by `h` before being shown or learned. The frame-jump detector is rate-relative rather than a fixed threshold, with the reasoning written at 3419-3424.
- **The clock correction writes nothing to the game.** `trackStartOffset` slews a private correction against GD's own inverse map with a deadband, a snap threshold, a time constant and a monotonicity floor. It is a read-only observer of a shared clock, so no other mod can be broken by it, and it degrades by holding the last correction rather than by guessing.
- **The un-hookable inlined setters are polled, not hooked.** `setStartPosObject` and `addToSpeedObjects` are `win inline`; we poll `(pointer, X)` and `count` from `postUpdate` instead. That is why a start-pos-switcher works with us without cooperation.
- **`MenuLayer`'s `bottom-menu` lookup is correct by construction, not by luck.** Geode core provides that ID from a `MenuLayer::init` hook pinned at `GEODE_ID_PRIORITY` (= 2000), and our post-original code at Normal runs after Geode's post-original code at 2000.
- **The shader is applied per node, not by patching `CCShaderCache`** (`render.cpp:34-36` says why: patching the shared program would restyle every `CCDrawNode` in the game, including the editor's), and the link is validated by asking GL directly rather than trusting cocos, with a fallback to the stock shader. `render.cpp:37-44` documents a real win32 hazard — reading `extern CC_DLL` data from a mod resolves to an import thunk, not the string — and inlines the vertex source to avoid it.
- **Every node ID is mod-namespaced with a double-add guard.**
- **`onQuit` clears the cross-level state that actually bit**, with the reasoning written down (the free-camera saved layer position bleeding into the *next* level's object layer is called out by name). The globals that survive level exit (`g_startKeyObj`, `g_segsFor`, `g_segsSpawn`) are raw pointers but are only ever compared, never dereferenced, after the level ends — so this is not a use-after-free.
- **The untrusted-input parsers are hardened with the specific attacks named in comments:** a top-level try/catch because a throw would unwind through GD's frames and terminate the process; explicit recursion-depth caps because a Windows stack overflow is uncatchable; every file-supplied length and count bounded by the bytes that actually exist; the `.slc` bit-packed exponent amplification (a 98-byte file requesting 2³¹ × 2¹⁵ expansions) identified and rejected; path traversal from server-supplied ids neutralised with the `fs::path::operator/` re-rooting hazard named; a 64 MB body cap before the write. "Downloads and parses untrusted third-party binaries inside a game hook" is the scariest sentence in this mod's description, and the code addresses it.
- **The parsers already read the `fps:` header and accept 1..2000**, so writing a real measured rate into recorded macros keeps old and new files readable with no format break.

## 4. Test protocol

These are the procedures that turn section 4 from predictions into results. Each is written to be runnable by someone who is not the author.

### 4.0 Setup, once

1. Clean Geode profile, GD 2.2081, **Click Indicators only**. Turn on **Debug logging** in our settings — several tests read `geode.log` rather than the screen.
2. Fix a test level set and use the *same* levels throughout, so results are comparable:
   - **L1** — a rated level with a downloaded macro, several clear isolated single jumps in the first 30 s, and at least one speed portal. Used for all timing tests.
   - **L2** — a long level (3+ min), many speed portals, **4 or more StartPos objects**, at least one after a speed portal and ideally one after a mirror portal.
   - **L3** — a **platformer** level with 3 or more StartPos objects and a macro.
   - **L4** — a level with a dual-mode section and a macro.
   - **L5** — a level you have **never played and never completed**, so GD's `m_attempts` and every third-party counter start at 0. Do not reuse L5 across tests; keep a list of fresh levels.
3. Learn the four log lines you will be reading, and grep for them rather than trusting the HUD:
   - `[CI-PRESS] x=… t=… markWx=… dx=… dt=… dxExpect=… sp=…` — `dt` is the **level-time** error in seconds, the ground truth for every timing test. The on-screen frame count is the derived value under test.
   - `[CI-ANCHOR] N presses, median ±X.XXXs -> offset ±X.XXX`
   - `StartPos x=… -> spawn at …s`
   - the `[CI-SYNC]` / `[CI-TAB]` diagnostics for the speed table and clock.
4. **Record a baseline before installing anything else.** On L1, click as exactly on the mark as you can, 30 times. Record the mean and spread of `dt`. Every later test compares against this. Repeat at 60 fps and at 240 fps with nothing else installed: if the 60 fps spread is roughly 4× the 240 fps spread, that quantisation is coming from the frame rate, not from you (2.1, fourth bullet), and you must not attribute it to another mod later.
5. Write results into this document, per row: `pass`, `fail`, or `refuted`. **`refuted` is a valid and valuable outcome** — several rows here are `low` confidence precisely so they can be struck.

### 4.1 The three tests that need no other mod at all

Run these first. Each can invalidate or confirm one of our own findings, and none requires installing anything.

1. **Vanilla attempt-label probe (highest value, two minutes).** Install nothing else. Safe mode **on**, macro loaded on L5, confirm the guide is drawing (safe mode only engages when `guideActive()` is true — non-empty macro **and** enabled **and** licensed — so with no macro nothing happens). Die 5 times, watching GD's own "Attempt N" label after each respawn.
   - **Pass:** the label advances 1, 2, 3, 4, 5.
   - **Fail:** it does not advance → we are freezing the **vanilla** label for every user with nothing else installed. That is a higher-priority bug than anything else in this document.
2. **Time Warp probe (2.1, last bullet).** Build or find a level with a 0.5× Time Warp trigger over a section containing several clicks. With nothing else installed, grade presses inside and outside the warped section and compare the reported frame count against the `dt` seconds in the log.
   - **Pass:** the frames figure inside the warp is consistent with the seconds.
   - **Fail:** frames inside the 0.5× section are about half what the seconds imply → 240 is wrong in vanilla GD, reachable with no other mod, and the measured-step fix is not optional.
3. **GL context loss (2.14).** With "Smooth lines" on and the overlay visible in a level, toggle fullscreen/windowed and change resolution.
   - **Pass:** the overlay still renders.
   - **Fail:** it goes invisible or garbled and stays that way until the game is restarted, with the setting still reading "on".

### 4.2 Click Between Frames

1. Install CBF. Start GD and grep `geode.log` for any hook-priority error attributable to `syzzi.click_between_frames` and `GJBaseGameLayer::handleButton` — this is the check that its `setHookPriority` line is inert. Then confirm we still receive presses at all: click in L1 and confirm `[CI-PRESS]` lines appear. **They should**, because `PlayLayer` does not override `handleButton` in 2.2081, so CBF's virtual call lands on the exact address we detour. If no `[CI-PRESS]` lines appear, stop — that is a total-blackout scenario the source analysis says cannot happen, and it invalidates the whole CBF section.
2. **Bias measurement (the main event).** Set CBF's "Disable CBF" to **ON**. Replay the L1 macro with a bot and read the `dt` values: they should cluster at 0.000 (this is the original calibration). Set "Disable CBF" to **OFF** and repeat.
   - **Fail:** the cluster moves to about **+0.0042** (one 240th) → `kPressLag` double-counts under CBF, and the whole CBF population is graded one frame late.
   - CBF's own README lists "does not work with bots" as a known issue, so **also run the human version**: 30 on-mark clicks with CBF off, mean `dt`; 30 with CBF on, mean `dt`. The difference of the two means is the injected bias; the spread is just you.
3. **Regime change mid-level.** Enter L1 from a StartPos with a downloaded macro and no measured map, so anchoring is active (confirm via `[CI-ANCHOR]`). With CBF disabled, make 3 deliberate on-mark presses so the anchor fixes; note the offset. Pause, flip "Disable CBF" to OFF in Geode's settings, resume. **Fail:** `dt` now clusters away from zero and stays there for the rest of the attempt. Repeat in the opposite direction, and repeat with "Click on Steps" instead.
4. **Precision Fix outliers.** Precision Fix **off**, 100 presses on L1, histogram the reported frame deltas. Precision Fix **on**, repeat. **Fail:** a small secondary cluster displaced by about one render frame appears in only one of the two runs. For the dropped-input half: with the recorder armed, tap immediately before dying, repeatedly, and check whether the saved macro's click count matches the taps you made.
5. **Physics Bypass:** run 4.3 with CBF as the carrier.
6. **Safe-mode composition.** Both safe modes on, beat a rated level: confirm no new best, no stars/orbs/diamonds/coins, no leaderboard submission, unchanged attempt counter. Then **both off** and confirm a normal completion does count and does submit — that second half is the check that neither mod left `m_isTestMode` stuck true. Then CBF's soft-toggle **off** (CBF active) with **both safe modes off**: confirm the percentage is still not saved, which isolates CBF's `savePercentage` hook as the cause and confirms the support note.

### 4.3 Physics tick rate (run once per carrier: CBF, Mega Hack, GDH)

1. Cap GD at 144 fps. Enable the carrier's physics/TPS bypass in its **2.1**-equivalent mode (4 steps/frame → 576 TPS). Play L1 for ~30 presses; record the on-screen frame deltas **and** the `dt` seconds side by side.

## 5. Fixes queued

These are changes worth making **regardless** of how the tests come out — either because the code is wrong on its own terms, or because the fix removes a whole class of interaction rather than one row. Ordered by value.

### Tier 1 — correctness, before any index submission

1. **Measure the physics step at runtime; delete the 240 constants.** Sample the step from a `PlayerObject::update` hook (P1 only) or from the smallest non-zero `m_levelTime` increment per step, take the **max** dt since the previous `postUpdate` (a sub-stepping mod splits a step into fractions, so max is the safe estimator), median-filter ~30 samples, require stability, clamp to `[30, 4000]`, and use it for `kPhysFps`, `kPressLag` and `xtSimulate`'s `dt`. This is self-contained, works for closed-source menus whose settings we can never read, and it also fixes the vanilla Time Warp case. Then:
   - **Make the unit visible instead of implicit.** Render "−2 frames @480", not "−2 frames", and show a one-shot notification when the measured rate differs from 240 by more than ~2%.
   - **When the rate is not ~240, stop claiming frames at all** — report milliseconds, and show a persistent banner ("physics tick rate 480/s; the macro was recorded at 240/s, timings are approximate") rather than a number the measurement cannot support. Optionally a "Require 240 TPS" setting, default on, that suppresses grading and recording off-rate while still drawing the cues.
   - **Skip calibration updates entirely off-rate**, exactly as the code already skips them when `g_startAlign != Exact`, and key persisted `cal-L` by rounded rate (`cal-L-480`) so the two populations never mix.
   - **Write the measured rate into recorded macro headers** (`fps: 480`, frames = round(t × rate)). Our own parsers already read the `fps:` line and accept 1..2000, so old and new files stay readable and third-party tools that honour the header get the truth. Alternatively refuse to save off-rate with a clear message — the precedent already exists at the alignment gate.
   - **Tag the persisted `xt-<levelID>` map with the rate** and refuse to load or extend a map whose tag does not match; at minimum, do not *append* off-rate, so a bypassed run can consume the map but never write to it.
   - Add the measured rate and `m_timeWarp` to the `[CI-PRESS]` debug line so support cases are diagnosable from a log.
2. **Save and restore `GameLevelManager::m_levelManagerDelegate`** instead of assign-and-null, and ignore callbacks that are not ours. This breaks GD's own level lists, not just other mods.
3. **Replace the attempts / stat `"2"` snapshot write-back with a delta-undo**, so the write is order-independent and cannot destroy a concurrent writer: `if (after > attemptsBefore) m_level->m_attempts = after - 1;` and `setStat("2", getStat("2") - 1)`. Do not round-trip a value through a hookable getter into a setter another mod may not hook. **Strongly consider dropping the attempt rollback entirely** — percentage, completion and leaderboard are the cheat vectors and are gated separately, our own comment records the rollback as an annoyance rather than a requirement, and dropping it removes 2.4, the whole tracker section of section 4, and the "attempt counter frozen" support load in one change. If it stays, make it a separate opt-in sub-setting (default off) worded to name the trackers it affects, and surface a running count of voided attempts in our own HUD so a user can reconcile by hand.
4. **Stop grading, anchoring and recording foreign input.** Two layers, because neither alone is sufficient:
   - *Behavioural, works everywhere including closed-source menus:* a replayed or autoclicked run has implausibly low variance, so if `sqrt(g_cal.Sbar)` collapses below a floor over a run of samples, freeze calibration and show "calibration paused (inputs look automated)". Reconcile the recorder's click count against a per-attempt counter so a swallowed or synthetic input is visible rather than silent.
   - *Cooperative, where an API exists:* Globed ships a soft-link API (`globed::api::game::isActive()`, `room::getSettings()->switcheroo`, with `isSafeMode()` as a correct superset fallback on 2.1.x since `needsSafeMode() == collision || twoPlayerMode || switcheroo`); Eclipse ships a config API (`eclipse::config::get<int>("bot.state")`, `player.autoclick`, `hasCheatsEnabled()`, `getEnabledCheats()`); CBF, xdBot and GDH expose their settings/saved values through `Loader::getLoadedMod(...)`. All are soft — no dependency, no version pin, default returns when absent. Use them to *name* the cause in the message, not to gate correctness.
   - While gated, keep drawing the cue but **freeze** the accuracy HUD, freeze `g_startOffset`, and refuse to arm the recorder — and say so on screen instead of producing garbage.
5. **Fix the mid-attempt macro swap:** defer the `g_actions`/`g_events` replacement to the next `resetLevel`, or at minimum latch `guideActive()` per attempt the way `safeTripped` already does, and reset `m_fields->nextTick` whenever the event array is rebuilt. A run must not stop counting because a download finished.

### Tier 2 — declare intent instead of racing

6. **Pin the four unpinned ordering-sensitive hooks.** Every one of these is a two-line change and each makes a behaviour deterministic that is currently decided by an unstable sort:
   - `GJBaseGameLayer::handleButton` → `Priority::VeryLate` (innermost), so we only ever observe inputs that actually reached the real function. That is the semantically correct choice for a mod whose entire job is measuring real inputs, and it matches what we already chose for `levelComplete`/`destroyPlayer`. Where a specific mod's ordering matters, `setHookPriorityAfter("GJBaseGameLayer::handleButton", "<mod id>")` works by ID and registers a `ModStateEvent` listener if the target is not loaded yet, so it is load-order independent.
   - `PlayLayer::postUpdate` → `Priority::VeryEarly` (= `VeryLatePost`), so our drawing runs after every other mod's camera work.
   - `PlayLayer::commitJumps` → `Priority::VeryLate`, matching its siblings, since it writes **before** the original and needs to be the last writer.
   - `PlayLayer::resetLevel` → decide after fix 3. With a delta-undo the choice matters much less; `VeryLate` forces the safer branch against relative-reader mods.
7. **Make `postUpdate` idempotent per rendered frame.** Cache `CCDirector::getTotalFrames()` in `Fields`; if unchanged, call the original and return before drawing or re-reading settings. Hoist the ~12 `getSettingValue` calls into a settings-changed listener. Accumulate `advance` across sub-steps rather than sampling `h` per call. This single guard fixes every sub-stepping mod at once, present and future.
8. **Harden the `h` estimator.** Persist it across respawns within a session (seed from the last converged value rather than resetting to 1.0); replace the `hFrames >= 15` gate with a convergence test; reject samples that cannot be real-time (require the advance to cover at least two physics steps, and discard `dW` below one render frame) instead of clamping an absurd ratio at 64×; freeze rather than adapt when the game is not continuously advancing.
9. **Rework `PauseLayer::keyDown`.** Resolve the contradiction between the comments at 4217-4220 and 4234-4237 **before** defending the `VeryEarly` priority (test 5.10 / the pause-dispatch question). Then: call the original **first** and act only on keys nobody else handled, or move to the keybinds API rather than a raw `keyDown` hook; make our pan and editor keys user-rebindable rather than hardcoded on the most contested keys in the game; and restore the previous keyboard-enabled state when the pause menu closes and when free camera is off, so we do not permanently widen key dispatch for every other mod in the process.
10. **Belt-and-braces safe mode.** Adopt the pattern another mod already found necessary: hook `GJGameLevel::savePercentage` at **Normal** (so it composes with theirs) and skip the original when `attemptIsUnsafe()`, guarded to the level currently being played. Better still, on an unsafe attempt do not call `PlayLayer::levelComplete()` at all and show our own "not counted" feedback — then no other mod's `levelComplete` hook fires and nothing downstream can log a completion. And be explicit either way: a notification on a suppressed completion saying that the game did not save it but third-party trackers may still record it, plus the same sentence in `about.md`.

### Tier 3 — data integrity in what we write and share

11. **Recorder.** Make alignment a property of the **buffer** (`recAlign`, demoted as frames are appended, carried through `recBank`) rather than a global read at save time. Rank buffers by **coverage** (last − first frame, or click count) not absolute end frame, and bank per spawn. Refuse or clearly tag saves made off-rate or with cheats active, naming what was active.
12. **Parsers.** Carry the button through: add `button` to `RawInput`/`Action`, populate from `btn` (defaulting to 1 when absent, so every other format keeps working), key `pairInto` on `(player, button)`, and require `button == 1` in the nearest-neighbour match — or draw directional inputs distinctly, which is the better long-term shape since a platformer branch already exists. Read the `bot` object and reproduce xdBot's own rule verbatim (`name == "xdBot"` and version < 2.3.6 → +1 frame). Store `bot.name`/`bot.version` on the loaded macro so the UI can show which tool produced a file and future per-tool quirks have somewhere to live. Make `pairInto` deterministic: `stable_sort` with press-before-release on equal frames, and drop degenerate zero-length pairs explicitly instead of relying on sort luck.
13. **Persisted map and calibration.** Gate `xt` appends on agreement with `canonTimeAtX` (within ~0.35 s) or on an explicit per-attempt `startedAtZero` flag, so no mod that teleports the player can poison a level's map permanently. Bucket `cal-L` per level (or per macro hash) rather than globally, so one bad file cannot mistime every level. Treat any backwards level-time discontinuity as an authoritative resync: re-run `syncStartOffset`, clear `g_anchorErrs`, drop `h` to its clamped default, rebuild the action index. Keep no per-attempt state outside `Fields`.
14. **Broaden and expose the anchor.** Allow the median anchor on the no-StartPos path too (it already absorbs exactly the class of constant bias that an unrecoverable per-macro offset produces), move the anchor push **below** the one-sample-per-action guard so duplicate `handleButton` calls cannot consume slots, and expose a manual per-macro "shift by N frames" nudge plus a visible `cal-L` with a reset button, so a poisoned calibration is diagnosable and recoverable without editing save files.
15. **Free camera.** Save and restore the object layer's **scale and rotation** as well as its position, or better, restore by undoing our own tracked pan (`g_fcPan` is already maintained and unused in the restore) so another mod's camera move is not destroyed. Invalidate the pending restore whenever the spawn identity or attempt number changed since the pan began, and clear `g_fcActive` from `resetLevel` as well as `onQuit`. For object visibility, record which objects we revealed and restore exactly those, instead of delegating to an out-of-band `updateVisibility(0.f)` that restores GD's intent rather than another mod's — and stop calling a hookable virtual at a moment GD never calls it.

### Tier 4 — hygiene, cost, and cosmetics

16. **Node placement.** Attach the level-page button to `right-side-menu` when the node exists (with the current absolute position as fallback), give it an ID, and let the owner's layout place it. Do **not** call `updateLayout()` on `bottom-menu`; add the child and let the owner's next pass handle it. Derive our scale from GD's own buttons or a fixed value, not from the tallest sibling. Step aside from a known neighbour by ID rather than by version check (e.g. shift up one button height when `dankmeme.globed2/playerlist-menu` is present). Add the same double-add guard on the pause UI that the other menus have, and skip all pause-UI construction when the pause layer is not actually going to be shown.
17. **Cost.** Move the macro parse off the level-entry hook, or cap the candidate scan (parse headers rather than whole files to pick a winner). Drop the StartPos from the speed-table invalidation key — the table provably does not depend on the spawn, which removes the per-switch rebuild entirely. Cache `timeForPos` per `(spawn, X)`. Move `xtSave()` off the `resetLevel` path onto `onQuit` plus a coarse timer, and coalesce rapid resolves by marking dirty for the next `postUpdate`.
18. **Small correctness.** Never build UI from inside `handleButton` — set a pending flag and show it from `postUpdate`, which runs after the whole physics loop. Take the recorded x from `m_lastPosition` or capture it in `postUpdate` rather than calling `getPositionX()` possibly mid-sub-step. Guard `g_btnDown` behind `PlayLayer::get()` so editor input cannot write it. Scope `g_slcTrimmed` to the chosen file so a rejected candidate cannot fire the restart warning. Dedupe the start-pos notifications by `(cause, spawn)` with a wall-clock floor, and raise the platformer one once per level entry rather than per resolve. Rebuild the GL program on context loss instead of latching a one-shot `tried` flag. Add a `$on_mod(Disabled)` teardown that removes our nodes and releases the retained program.
19. **`mod.json` and repository.** Add `repository` and `issues` links — for a submission whose stated blocker is long-term maintainability, a public issue tracker is the cheapest evidence available. Do **not** add hard `incompatibilities` entries against Click Between Frames, Eclipse, Mega Hack, Globed or BetterInfo: the problematic behaviour is in every case an opt-in, default-off setting or a feature most users never touch, the install bases are in the millions, and Geode's incompatibility syntax cannot express "only when setting X is true". Reserve the key for a case where the mods genuinely cannot coexist, and use runtime detection plus an honest in-game notice for everything else. Where a soft note is warranted (Mega Hack is the strongest candidate, given it hooks a strict superset of our surface and persists a physics TPS between sessions), a `conflict`-severity entry is right and a `breaking` one is not.
20. **Keep the regression history.** The comments recording *why* a constant or an ordering exists (the empirical origin of `kPressLag`; the mirror screen-space ordering and the bug it fixed; the rate-relative jump detector; the `onQuit` clears and which bug motivated each; the `win32 extern CC_DLL` hazard; the named parser attacks) are the most useful artefact a maintainer can leave and are directly responsive to the maintainability question. Add one for the `m_isTestMode` nesting and the 64× `h` clamp, both of which are load-bearing specifically for coexistence and are exactly the kind of thing a future refactor would simplify away.

## 6. What still needs a human, and cannot be answered from source

Listed separately so it is not mistaken for something that was checked. Each of these is a claim in this document that rests on an assumption I could not verify:

- Whether `PauseLayer` dispatches `keyDown` without `setKeyboardEnabled(true)`. **This decides whether our `VeryEarly` priority is justified or vestigial**, and it is the priority a moderator is most likely to challenge.
- Whether GD's own in-level attempt label derives from `m_level->m_attempts` (5.1 step 1). If it does, we freeze the vanilla label with no other mod installed.
- Whether `m_levelTime` has already been incremented for the step by the time a sub-stepping input mod dispatches `handleButton` from inside `PlayerObject::update`. `GJBaseGameLayer::update` is a bare address in the bindings with no reconstructed body, so the position of the increment relative to `PlayerObject::update` is not documented anywhere I could find. This decides whether the CBF one-frame bias is real.
- What `PlayLayer::resetLevelFromStart` does internally — specifically whether it nulls `m_startPosObject` and whether it clears `m_checkpointArray`. Our own comment asserts the former; the `xt`-poisoning row depends on it.
- Whether GD reaches `GJGameLevel::savePercentage` on any path that does not consult `m_isTestMode` (5.11).
- The exact meaning of `GameStatsManager` stat `"2"` — confident it is global, less confident it is specifically total attempts — and whether `setStat` marks the stat dirty for submission or re-triggers achievement/quest evaluation.
- Whether `m_player1` can be null at a moment `handleButton` fires (the Geode reimplementation of `isGameplayActive()` dereferences it, and a crash there looks like a Geode bug).
- Whether GD or Geode ever recreates the GL context on Windows for a fullscreen or resolution change.
- Whether any installed mod actually moves the camera or object layer in post-original `postUpdate` code. The mechanism is certain; the observability is not.
- Whether Geode dispatches keybind events while a `PauseLayer` is up (this decides whether the free-camera-versus-start-pos-switcher row exists at all).
- Eclipse Menu's 1.9.x implementation, Mega Hack's per-hook priority values, and the 2.2081 xdBot fork's actual code. All three are marked `unknown` where it matters and rest on binary evidence or on older forks.
- Every "class of mod" row in section 4. Those claims are mechanism-level. No third-party mod in those categories was read, none is named, and each should be confirmed against actual index listings before being asserted publicly.
